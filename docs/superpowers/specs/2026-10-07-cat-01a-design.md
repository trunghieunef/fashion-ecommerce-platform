## 1. Mục tiêu và tiêu chí thành công

OPS quản lý được category, brand, product và variant qua `/admin/api/v1/catalog/**`; publish
chỉ thành công khi product đủ điều kiện; SKU unique và bất biến; mỗi variant mới sinh đúng
một `VARIANT_CREATED` trong outbox cùng transaction để inventory (INV-01) đăng ký SKU kho 0
trước khi nhập kho. Thành công = test integration PostgreSQL thật cho các case ở §8 PASS,
mutation thật, contract validate, docs đồng bộ.

## 3. Schema — V002 và follow-up V003 (append-only, giữ migration đã áp dụng)

Theo 05 §5, bảng/cột giữ tên của 05:

- `categories` (T): `parent_id` FK self, `name_vi`, `name_en`, `slug` UNIQUE, `sort_order`,
  `status` ACTIVE/INACTIVE, CHECK `parent_id <> id`, thêm `version bigint = 0` cho PUT.
- `brands` (T): `name`, `logo_url?`, `status`, thêm `version bigint = 0`.
- `products`: thêm `category_id` FK, `brand_id?` FK, `description_vi/en text = ''`,
  `base_price bigint` CHECK ≥ 0, `tags text[] = '{}'`, `published_at?`,
  `sold_quantity bigint = 0` CHECK ≥ 0. Dòng có sẵn từ read sample được gán vào một category
  seed `uncategorized` (UUID cố định) và `base_price = 0` trước khi đặt NOT NULL; dòng sample
  ACTIVE giữ nguyên trạng thái. CHECK status của `V001` (DRAFT/ACTIVE/INACTIVE) giữ nguyên.
- `product_variants` (T): `product_id` FK, `sku varchar(64)` UNIQUE không phân biệt casing qua V003, `size`, `color`,
  `price_override bigint?` CHECK ≥ 0, `weight_grams int` CHECK > 0, `status`, `version`;
  UNIQUE `(product_id, size, color)`.
- Trigger `BEFORE UPDATE` trên `product_variants` báo lỗi nếu `sku`, `size`, `color` hoặc
  `product_id` thay đổi — bất biến được giữ ở DB, không chỉ ở code.
- `outbox_events`, `idempotency_requests`, `audit_logs`: chép DDL từ
  [platform-durability](../../../services/platform-durability/README.md) / user-service;
  `REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs FROM catalog_runtime`.
- Index thêm: `products(category_id, status, published_at, id)` theo 05; các index query
  khác của 05 để CAT-02 khi có truy vấn thật.

Không có `DELETE` trên catalog từ API; runtime role vẫn có quyền DELETE theo default
privileges hiện có nhưng không có đường code dùng.

## 4. API admin

Base `/admin/api/v1`, catalog-service phục vụ trực tiếp path này; Gateway thêm route
`catalog-admin` cho `/admin/api/v1/catalog/**`. Mọi endpoint yêu cầu Bearer có permission
`catalog.write` (OPS): verify chữ ký ES256 + `kid` + `exp` bằng `AccessTokenVerifier` với
`CATALOG_JWT_PUBLIC_KEYS` (cùng giá trị `USER_JWT_PUBLIC_KEYS`), không gọi user-service
(08 ADR-21: thu hồi quyền trễ tối đa 15 phút). Thiếu/sai token → 401; thiếu permission → 403.

| Method / path | Input → output |
|---|---|
| GET /catalog/categories | Toàn bộ cây (≤ 2 cấp, số lượng nhỏ), không phân trang |
| POST /catalog/categories | `parent_id?`, `name_vi`, `name_en`, `slug`, `sort_order?` + key → category |
| PUT /catalog/categories/{id} | Các field trên + `status`, `expected_version` → category |
| GET /catalog/brands | Toàn bộ brand, không phân trang |
| POST /catalog/brands; PUT /catalog/brands/{id} | `name`, `logo_url?` (+ `status`, `expected_version` khi PUT) |
| GET /catalog/products | `page` (từ 1), `size` (mặc định 20, ≤ 100), `status?` → items + `total` |
| POST /catalog/products | `category_id`, `brand_id?`, `name_vi/en`, `slug`, `description_vi/en?`, `base_price`, `tags?` + key → product DRAFT |
| GET /catalog/products/{id} | Product + variants |
| PUT /catalog/products/{id} | Field nội dung như POST + `expected_version`; không đổi `status` (dùng publish/unpublish) |
| POST /catalog/products/{id}/publish | `expected_version`, `reason?` + key → ACTIVE |
| POST /catalog/products/{id}/unpublish | `expected_version`, `reason?` + key → INACTIVE |
| POST /catalog/products/{id}/variants | `sku`, `size`, `color`, `price_override?`, `weight_grams` + key → variant |
| PUT /catalog/variants/{id} | `price_override?`, `weight_grams`, `status`, `expected_version` → variant |

Quy ước (03 §1.2/1.3):

- Mọi POST bắt buộc `Idempotency-Key` (1–128 ký tự); `actor_key = user:<id>`, operation theo
  endpoint (+ path id), `request_hash` = SHA-256 của body đã normalize phía server. Cùng key
  cùng body → response đã lưu; khác body → 409 `CONFLICT`. `begin` chạy trong cùng transaction
  nghiệp vụ như user-service: request trùng chờ khóa PK rồi thấy COMPLETED, không lộ
  PROCESSING; lỗi rollback cả bản ghi idempotency để retry cùng key chạy lại.
- Mọi PUT và publish/unpublish bắt buộc `expected_version`: thiếu → 400, lệch → 409
  `VERSION_CONFLICT`. Thành công tăng `version` một đơn vị.
- `reason` tùy chọn (≤ 500), ghi vào audit.
- Response/lỗi theo envelope `common.yaml`; JSON snake_case; tiền là integer VND.
- Không có endpoint DELETE; ngưng bằng `status = INACTIVE` (variant/category/brand) hoặc
  unpublish (product).

Validation field: tên ≤ 255; slug `^[a-z0-9]+(-[a-z0-9]+)*$` ≤ 160; `base_price`,
`price_override` 0..9 223 372 036 854 775 807 (bigint, không float); `weight_grams`
1..2 147 483 647; SKU 1–64 ký tự `^[A-Za-z0-9][A-Za-z0-9._-]*$`; size/color 1–50; tags ≤ 20,
mỗi tag 1–50; description ≤ 20 000 ký tự sau sanitize. FK category/brand không tồn tại → 400
field error. SKU được `String.strip` rồi kiểm ASCII trước khi uppercase `Locale.ROOT`;
giá trị uppercase dùng trước hash idempotency và trong DB/audit/outbox. Trùng slug/SKU/bộ
product-size-color → 409 `CONFLICT` kèm field; SKU không phân biệt casing, kể cả race.
Chủ dự án duyệt follow-up PR14 chỉ chuẩn hóa SKU mới: V003 thêm unique index
`upper(sku COLLATE "C")` + BEFORE INSERT guard uppercase ASCII, không sửa V001/V002.
SKU legacy, audit/outbox và response/hash cũ không backfill; UPDATE trường mutable vẫn được.
Retry đổi casing replay cùng data/status; key legacy lấy SKU nguyên gốc từ response đã lưu
để kiểm hash cùng các field request còn lại. Đổi field khác vẫn 409; metadata mới, không side effect.
Collision casing làm migration dừng để quyết định dữ liệu riêng, không tự merge hoặc đổi identity.

## 5. Quy tắc nghiệp vụ

- **Product state:** tạo luôn DRAFT. Publish: DRAFT|INACTIVE → ACTIVE, đặt `published_at`
  lần đầu. Unpublish: ACTIVE → INACTIVE. Cạnh khác → 409 `CONFLICT`. Sửa nội dung product
  ACTIVE được phép, giữ ACTIVE.
- **Điều kiện publish** (kiểm dưới khóa dòng product): `name_vi`, `name_en` không rỗng;
  category ACTIVE; brand ACTIVE nếu có; ≥ 1 variant ACTIVE. Không đạt → 400
  `VALIDATION_ERROR` liệt kê lý do, trạng thái không đổi. Điều kiện ảnh: CAT-03.
- **Variant:** `sku`, `size`, `color` bất biến sau khi tạo; sửa được `price_override`,
  `weight_grams`, `status`. Thêm variant được cả khi product DRAFT/ACTIVE/INACTIVE.
- **Category:** tối đa 2 cấp (parent phải là gốc); không tự làm parent; category đã có con
  không được gắn làm con. Ngưng category không lan sang product; publish kiểm category ACTIVE.
- **HTML:** `description_vi/en` qua jsoup `Safelist.basic()` + `h2`, `h3`; link chỉ
  http/https, ép `rel="nofollow noopener"`. Lưu HTML đã làm sạch, không từ chối request vì có
  tag bị loại.
- **Audit:** mọi mutation ghi `audit_logs` cùng transaction (`actor_id`, action như
  `catalog.product.publish`, resource, `reason`, before/after tối thiểu, `request_id`).

## 6. Event `VARIANT_CREATED`

Trong một transaction: khóa product `FOR UPDATE` → insert variant → tăng `products.version` →
`OutboxRepository.append` với `aggregate_type = product`, `aggregate_id = product_id`,
`aggregate_version` = version product mới, topic `catalog.events`, partition key
`product_id`, payload `{product_id, variant_id, sku, version}` theo
`catalog-events.schema.json#/$defs/VariantCreated` (`version` = version variant, 0) → audit →
kết quả idempotency. Lỗi bất kỳ rollback cả variant lẫn outbox. Mỗi variant đúng một event;
sửa variant không phát lại. Khóa product cũng tuần tự hóa `aggregate_sequence`.

## 8. Kiểm thử (TDD, PostgreSQL Testcontainers)

- Auth: không token 401; token hết hạn/sai key 401; thiếu `catalog.write` 403.
- Version: thiếu `expected_version` 400; stale 409; hai PUT song song cùng version → đúng một
  thành công.
- Idempotency: cùng key/body trả cùng resource, không tạo bản thứ hai; khác body 409.
- SKU: trùng 409; hai request song song cùng SKU → một thành công, một 409; `UPDATE sku`
  trực tiếp bằng SQL bị trigger từ chối; PUT variant không có field đổi SKU.
- Publish: thiếu variant ACTIVE / category INACTIVE → 400, status vẫn DRAFT; unpublish rồi
  publish lại; cạnh sai 409.
- Outbox: tạo variant → đúng một dòng `VARIANT_CREATED` payload hợp lệ theo schema; lỗi sau
  insert (vd. idempotency/audit) rollback cả variant và outbox; retry cùng key không thêm dòng.
- Sanitize: `<script>`, `onerror`, `javascript:` bị loại; tag cho phép giữ nguyên.
- Audit: runtime role không UPDATE/DELETE được `audit_logs`.
- Migration: dòng sample `V001` còn đọc được qua public API sau `V002`.
- Gateway: route admin catalog tới catalog-service; header danh tính client vẫn bị loại.
- Contract: `catalog.yaml` thêm paths admin, `validate-contracts.sh` PASS.
- Mutation thật cho trigger SKU, check version, điều kiện publish, outbox trong transaction.
- Smoke local: OPS synthetic tạo category → product → variant → publish qua Gateway.
